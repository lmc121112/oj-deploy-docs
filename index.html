Tài liệu Vận hành & Sử dụng Hệ thống Online Judge

Hệ thống Online Judge được thiết kế theo kiến trúc tách rời giữa giao diện Web, cơ sở dữ liệu hàng đợi và lõi chấm bài cô lập sandbox, gồm 3 thành phần chính:

oj-web-app

Frontend Next.js + Ace Editor

Giao diện nộp bài, quản trị đề/kỳ thi, render đề bài Markdown + KaTeX và theo dõi chấm real-time.

Supabase

PostgreSQL & Hàng đợi

Lưu trữ tài khoản, đề bài, test cases, kỳ thi, code mẫu và hàng đợi bài nộp Pending → Finished.

oj-judge-core

Lõi chấm C++ & Isolate

Biên dịch và chạy code thí sinh trong sandbox isolate, đo thời gian (ms), bộ nhớ (KB) chính xác.

Luồng xử lý một bài nộp

  1. Thí sinh gửi mã nguồn trên Web (oj-web-app); bản ghi mới được tạo trong bảng submissions với trạng thái Pending.
  2. Worker chấm bài (trên VPS hoặc GitHub Actions) lấy bài Pending, tải test case từ bảng test_cases (hoặc thư mục tests/), biên dịch và thực thi từng test trong sandbox isolate.
  3. Lõi judge.cpp cập nhật kết quả từng test (test_results), thời gian chạy lớn nhất (exec_time_ms), bộ nhớ (memory_kb) và chuyển trạng thái sang Finished.
  4. Trình duyệt của thí sinh tự động cập nhật kết quả mỗi 1 giây mà không cần tải lại trang.

2. Kho Tải Tệp Cấu hình & Biểu mẫu (Downloads)

Tải trực tiếp toàn bộ tệp SQL khởi tạo cơ sở dữ liệu, GitHub Actions workflows, script dịch vụ VPS và mẫu soạn đề Markdown + LaTeX chỉ với một cú nhấp chuột (hoặc bấm Xem trước để kiểm tra nội dung trước khi tải):

A. Nhóm Triển khai GitHub Actions (Miễn phí)

schema-actions.sql SQL

Schema PostgreSQL khởi tạo đầy đủ bảng dữ liệu cho Supabase khi dùng Worker GitHub Actions.

build-vendor.yml YAML

Workflow biên dịch sẵn vendor/bin/judge và isolate trên Ubuntu runner.

judge.yml YAML

Workflow tự động lấy bài nộp Pending từ Supabase và chấm định kỳ hoặc thủ công.

B. Nhóm Triển khai Máy chủ VPS (Chấm thời gian thực 24/7)

schema-vps.sql SQL

Schema PostgreSQL tối ưu cho VPS worker chạy liên tục và đồng bộ kết quả tức thì.

worker-vps.sh BASH

Script vòng lặp daemon gọi lõi judge kiểm tra hàng đợi bài nộp liên tục trên Linux.

oj-judge.service SYSTEMD

Tệp cấu hình dịch vụ systemd giúp worker tự khởi động cùng VPS và tự khôi phục khi lỗi.

C. Tệp Mẫu Môi trường & Soạn Đề bài

.env.local.example ENV

Mẫu biến môi trường kết nối Supabase cho ứng dụng web Next.js (oj-web-app).

mau-de-bai.md MARKDOWN

Khuôn mẫu soạn đề bài chuẩn Markdown + LaTeX + bảng ví dụ có sẵn <br> để dán vào Admin.

4. Thiết lập Cơ sở dữ liệu Supabase

Tạo một dự án mới trên Supabase, mở mục SQL Editor và chạy tệp schema tương ứng (tải ở Mục 2):

  • schema-actions.sql: Dùng khi chấm bằng GitHub Actions.
  • schema-vps.sql: Dùng khi chấm bằng VPS riêng.
Lấy khóa API: Vào Project Settings → API để sao chép Project URL, khóa anon public (dùng cho Frontend) và khóa service_role (chỉ dùng cho Worker chấm bài ở backend).

5. Triển khai Worker chấm bằng GitHub Actions (Miễn phí)

  1. Tạo repository chứa mã nguồn từ oj-judge-core.
  2. Đặt 2 tệp build-vendor.yml và judge.yml (tải ở Mục 2) vào thư mục .github/workflows/.
  3. Vào Settings → Secrets and variables → Actions và thêm 2 Secrets: SUPABASE_URL và SUPABASE_SERVICE_KEY.
  4. Chạy workflow Build Vendor một lần duy nhất để biên dịch sẵn vendor/bin/judge và vendor/bin/isolate.

6. Triển khai Worker VPS chạy 24/7 (Khuyên dùng cho Kỳ thi)

Bước 1: Cài đặt trình biên dịch & biên dịch lõi chấm

bash (Ubuntu / Debian) 
sudo apt update && sudo apt install -y build-essential libcurl4-openssl-dev libcap-dev git python3 openjdk-17-jdk
git clone <link-repo-oj-judge-core> /opt/oj-judge
cd /opt/oj-judge
g++ -std=c++17 -O2 judge.cpp -lcurl -o vendor/bin/judge
chmod +x vendor/bin/judge vendor/bin/isolate

Bước 2: Kích hoạt systemd service

Tải tệp worker-vps.sh và oj-judge.service ở Mục 2, cấu hình URL/Key Supabase rồi kích hoạt:

bash 
sudo cp worker-vps.sh /opt/oj-judge/worker-vps.sh
sudo chmod +x /opt/oj-judge/worker-vps.sh
sudo cp oj-judge.service /etc/systemd/system/oj-judge.service
sudo systemctl daemon-reload
sudo systemctl enable --now oj-judge.service
sudo systemctl status oj-judge.service

7. Triển khai Giao diện Web (oj-web-app) lên Vercel

  1. Đẩy mã nguồn oj-web-app lên GitHub.
  2. Truy cập Vercel, chọn Add New Project và nhập repository oj-web-app.
  3. Khai báo 2 biến môi trường: NEXT_PUBLIC_SUPABASE_URL và NEXT_PUBLIC_SUPABASE_ANON_KEY (xem tệp mẫu .env.local.example ở Mục 2).
  4. Nhấn Deploy để xuất bản trang web.

9. Cấu hình Input/Output & Quản lý Test Cases

  • Standard I/O (stdin / stdout): Thí sinh đọc từ bàn phím chuẩn và in ra màn hình chuẩn.
  • File I/O (file): Khi đặt io_mode = 'file' và io_filename = "BAI1", trang đề bài sẽ tự hiển thị hộp nhắc nhở thí sinh đọc từ BAI1.in và ghi ra BAI1.out.
  • Ví dụ mẫu tự động: Test có test_order nhỏ nhất sẽ tự động được lấy làm Ví dụ mẫu ở cuối trang đề bài (trừ khi bật hide_tests).

10. Tổ chức Kỳ thi (Chế độ ICPC & OI)

  • Khung thời gian tự động: Trước start_time, thí sinh vào bài sẽ thấy màn hình khóa kèm đồng hồ đếm ngược. Sau end_time, bài tự động khóa nộp bài (tài khoản admin luôn được phép xem và nộp thử mọi lúc).
  • Giới hạn danh sách thí sinh (restrict_users): Chỉ những tài khoản nằm trong mảng allowed_users mới truy cập được kỳ thi.
  • Chế độ ẩn điểm OI (hide_grading): Ẩn toàn bộ kết quả chấm từng test trong thời gian diễn ra kỳ thi và tự động công bố khi hết giờ.

11. Quản lý Code Mẫu Mặc định (Language Templates)

Hệ thống ưu tiên lấy code mẫu từ bảng system_settings (khóa code_templates do Admin chỉnh sửa trực tiếp trên web), sau đó mới lấy từ bảng language_templates.

12. Quy trình Làm bài & Nộp bài cho Thí sinh

  1. Đăng nhập tài khoản ở góc trên bên phải màn hình.
  2. Mở bài tập từ mục Bài tập hoặc từ danh sách bài trong Kỳ thi (Contests).
  3. Kiểm tra kỹ mục Input/Output (stdin / stdout hay đọc/ghi tệp .in / .out).
  4. Chọn ngôn ngữ lập trình, nhập mã nguồn trên Ace Editor và nhấn 🚀 Nộp bài.

13. Giải thích Các Mã Trạng thái Chấm (Verdicts)

Mã Ý nghĩa Nguyên nhân thường gặp & Cách xử lý
AC Accepted (Chính xác) Chương trình vượt qua toàn bộ bộ test trong giới hạn thời gian và bộ nhớ.
WA Wrong Answer (Sai kết quả) Kết quả in ra khác đáp án chuẩn. Kiểm tra trường hợp biên, tràn số (long long) hoặc định dạng xuống dòng.
TLE Time Limit Exceeded (Quá thời gian) Thuật toán chạy chậm hơn time_limit_ms. Cần tối ưu độ phức tạp hoặc bật Fast I/O.
MLE Memory Limit Exceeded (Quá bộ nhớ) Khai báo mảng quá lớn hoặc đệ quy quá sâu vượt quá memory_limit_mb.
RE Runtime Error (Lỗi thực thi) Truy cập ngoài chỉ số mảng, chia cho 0, hoặc trả về mã thoát khác 0.
CE Compilation Error (Lỗi biên dịch) Sai cú pháp ngôn ngữ. Bấm xem chi tiết bài nộp để đọc thông báo lỗi biên dịch.
G Grading / Pending (Đang chấm) Bài nộp đang nằm trong hàng đợi hoặc đang được lõi chấm xử lý.

14. Quy chế Thi & Xem Chi tiết Từng Test

  • Thanh điều hướng nhanh: Khi làm bài trong kỳ thi, cột bên phải hiển thị đồng hồ đếm ngược và danh sách đánh số 1, 2, 3... để chuyển bài nhanh.
  • Xem chi tiết bài nộp: Trong trang Các bài nộp, nhấn nút Chi tiết trên mỗi bài nộp để xem Input, Expected Output, Actual Output, thời gian và bộ nhớ của từng test.
